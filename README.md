# Generic daily private delivery

Standard-library Python and standard public GitHub-hosted Actions runners deliver a prepared queue to one private Telegram chat. No AI, polling bot, public content publication, external dependencies, paid runners, caches or uploaded artifacts are involved.

The public repository must contain only this generic source, synthetic tests and opaque delivery state. Never commit actual queue contents, Telegram file identifiers, credentials, recipient identifiers or private response bodies. Configure repository secrets `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` and `QUEUE_JSON`. The workflow uses the automatic repository-scoped `GITHUB_TOKEN` for state writes. Keep write access limited to trusted maintainers.

`QUEUE_JSON` is raw JSON with a random 32-character lowercase hexadecimal `queue_id`, `timezone` set to `Europe/Berlin`, and `days`. Each day has an ISO `date` and ordered `items`. Items are either `{ "method": "sendVideo", "file_id": "…", "caption": "…" }` or `{ "method": "sendMessage", "text": "…" }`. Use a video-type file identifier obtained by the same bot, with the original upload verified separately. Text arrives unchanged and without formatting mode or prefixes. Consecutive sends are paced at least 1.1 seconds apart. Validate every queued item before any delivery. Repository secrets are limited to 48KB. Queue values are never printed, including on validation errors; do not enable shell tracing or add payload logging.

Before activation, initialize branch `delivery-state` with `ledger.json` containing exactly `{ "version": 1, "items": {} }`. Do not initialize state automatically during a run. Each item uses a key composed of random queue ID, date, daily/preview mode and item index. Values are only `pending` or `sent`. The dispatcher durably reserves `pending` through a GitHub Contents API compare-and-swap update before sending, then records `sent` only after a confirmed Telegram response. The ledger contains no Telegram message IDs or payloads.

A timeout, crash, cancelled run, failed acknowledgment write or stale concurrent write stops delivery. An existing pending item blocks every subsequent automatic attempt at that item; it never expires. A completed item is skipped. This favors avoiding duplicate sends and can omit a delivery after an interruption. Telegram and GitHub do not form an atomic transaction. Inspect the private conversation before recovery; never blindly delete a pending entry. A trusted operator can mark it sent after confirming receipt, or explicitly clear it after establishing it was not sent. Preserve all other state. Never reset the state branch or change an existing queue ID/item order/content to bypass a receipt. If restoring a backup, reconcile with the private conversation first.

Scheduled runs select only today's Berlin date, after 17:30, and only if that date exists in the queue. The two UTC schedules run at 17:30 and 18:00 Berlin during winter. Summer delivery is one hour later unless the workflow is updated. There is no backlog catch-up and no delivery on dates outside the queue. An explicit preview date outside the queue fails without sending. GitHub schedules may be delayed or dropped; the second invocation catches a missed first invocation without repeating completed deliveries. After the prepared queue ends, remove or disable the workflow to avoid unnecessary no-op runs.

Manual dispatch defaults to a network-free dry run. Every manual dispatch uses separate **preview** receipts, including when a date is supplied. Unchecking dry run sends that preview once; its completion does not consume the daily packet. A second preview of the same day is skipped. Workflow concurrency covers both modes. The five-minute job limit leaves a durable pending reservation if an interrupted job had begun a send.

Run `python3 -m unittest discover -s . -p 'test_*.py'` from this directory. Deployment verification should include a hosted dry run, an explicitly requested hosted preview and a rerun showing zero newly sent items. Confirm scheduled invocation separately; manual success does not establish recurring arrival.

Standard public runners are [free independently of included compute usage](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Public schedules can be [disabled after 60 days without repository activity](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). [Secret limits](https://docs.github.com/en/actions/reference/security/secrets) and [Telegram video delivery](https://core.telegram.org/bots/api#sendvideo) are documented by their providers.
